\section{Cognitive Diagnostics: Probing the Reasoning Trace}
\label{sec:cognitive}

\subsection{Repository-Level Reasoning and the Aggregation Deficit}

As agentic systems are deployed on increasingly complex tasks---particularly in software engineering---evaluation must probe not just whether the agent produces correct output, but whether it can reason effectively about large, interdependent code systems.

The Agent GPA framework paper~\citep{agent_gpa} includes analysis of a verification-centric diagnostic approach---which it describes under the label \textbf{RepoReason}---designed to evaluate repository-level reasoning. Rather than testing code generation, this approach uses Abductive Assertion Verification: by masking unit-test assertions and requiring the model to derive values that satisfy them, it tests the agent's ability to mentally reconstruct execution history across multi-file systems.

This evaluation approach is significant because it targets the kind of reasoning that production agents must perform: understanding how changes in one file propagate through dependencies, predicting the behavior of code without executing it, and synthesizing information across multiple modules.

Within the evaluation setup described by \citet{agent_gpa}, the following patterns were observed. These are findings specific to that benchmark's task distribution and evaluation conditions; they should not be generalized as universal architectural laws without replication across other setups:

\begin{description}
    \item[The Cliff Effect] Reading comprehension accuracy dropped sharply when code volume exceeded approximately 600 lines in the evaluated tasks. This is reported as a precipitous rather than gradual decline within this benchmark---though the exact threshold may shift with model version, context window size, or task type.
    \item[The Aggregation Deficit] Accuracy declined as ``integration width'' increased---meaning the number of cross-file dependencies the agent had to synthesize. This pattern is consistent with the structure of real production codebases, but its precise magnitude depends on the benchmark's specific dependency topology.
    \item[Consistency Decay] Models exhibited a significant loss of consistency beyond approximately 100 execution steps in a single trajectory within this benchmark's evaluation context. This is a notable finding, though the 100-step threshold is dataset-specific and should not be treated as a fixed architectural constant.
\end{description}

These patterns are not necessarily model-specific quirks, but their robustness across different codebases, models, and task distributions requires further empirical study. They point to important classes of failure mode that evaluators should actively probe, even if the precise thresholds remain to be established.

\subsection{The ``Cliff Effect'' and Simulation Depth Limits}

The cliff-like performance pattern described above deserves particular attention because, if confirmed across broader evaluations, it would represent a qualitative rather than quantitative failure mode. Unlike gradual performance degradation, a cliff effect means that an agent can appear fully competent right up to the point where it catastrophically fails---a pattern that routine benchmark sampling might miss entirely.

Pending broader empirical replication, practitioners should consider the following implications:

\begin{enumerate}
    \item \textbf{Interpolation may be unreliable.} If an agent performs well on short codebases and poorly on long ones, performance at intermediate lengths cannot be safely assumed. The degradation point may vary by model, task type, and codebase structure.
    \item \textbf{Benchmark scope affects generalizability.} A benchmark constrained to short or simple codebases will produce results that may not transfer to the complexity levels common in production environments.
    \item \textbf{Explicit complexity bounds are prudent.} Until performance-cliff behavior is better characterized, organizations deploying agents on code-heavy tasks should define and enforce maximum complexity thresholds rather than relying on benchmark extrapolation.
\end{enumerate}

The consistency-decay pattern at extended trajectory lengths has similar practical implications. The approximate 100-step figure reported by \citet{agent_gpa} should be treated as one data point in a specific evaluation context; the core concern---that long-running tasks may accumulate reasoning degradation that shorter tasks do not---is the actionable insight. This must be accounted for in both evaluation and deployment design:
\begin{itemize}
    \item Break long workflows into shorter segments with verification checkpoints.
    \item Implement intermediate validation steps that can catch reasoning drift before it compounds.
    \item Monitor trajectory coherence in real-time and escalate to human oversight when degradation is detected.
\end{itemize}

\subsection{Agent GPA: Decomposing the Goal-Plan-Action Cycle}

Traditional evaluation treats task completion as a monolithic outcome. But agentic behavior can be decomposed into three distinct cognitive phases, each of which can fail independently~\citep{agent_gpa}:

\begin{enumerate}
    \item \textbf{Goal comprehension}: Does the agent correctly understand what it is being asked to do?
    \item \textbf{Plan formulation}: Does the agent devise a sensible strategy for achieving the goal?
    \item \textbf{Action execution}: Does the agent correctly implement the plan through tool calls and environmental interactions?
\end{enumerate}

The \keyword{Agent GPA} (Goal-Plan-Action) framework evaluates each phase independently, producing a profile rather than a single score. Figure~\ref{fig:agent_gpa} illustrates this decomposition.

An agent with a high Goal score but low Action score understands what to do but cannot execute it. An agent with a high Action score but low Goal score can execute flawlessly---but on the wrong task. These are fundamentally different problems requiring fundamentally different solutions.
